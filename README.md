# 《LLMOps in Action》

![读者](https://img.shields.io/badge/读者-传统运维与SRE-2C7A7B?style=flat) ![篇幅](https://img.shields.io/badge/篇幅-六篇·27章·148节-4A5568?style=flat) ![稿件](https://img.shields.io/badge/稿件-首稿校订中-B7791F?style=flat) ![案例环境](https://img.shields.io/badge/案例环境-GPU-4C51BF?style=flat)

写给国内传统运维与 SRE 工程师的大模型训练与推理工程化书稿。

全书用一套自下而上的色阶标记技术栈层次：石墨（一 底座）、青（二 AI IaaS）、蓝（三 模型生产）、靛（四 模型服务化）、紫（五 MaaS 与智能体）、灰（六 横切治理）；六篇各配一枚同色徽标，进度状态另用绿、黄、灰三色。徽标由 shields.io 生成，只携带篇目名称与状态，不含任何正文内容。

作者参与过多个万卡级智算项目，从硬件交付一路做到稳态运行。这段经历里最常见的一幕，不是某个技术点把人难住，而是同期转岗的同事被同样两件事绊住：不知道该按什么顺序学，以及正在学的东西马上就要过期。这本书是把这两件事摊开来写的。

## 冲突在哪里

传统运维转到大模型训推上，冲突有三层，越往下越难说出口。

责任对象换了。过去对一次发布、一段可用性曲线负责；现在要对一张卡跑出了多少有效算力、一次请求花了多少钱负责。指标的语言整个换掉：训练侧看 MFU 与通信占比，推理侧看首 Token 时延、逐 Token 间隔与每卡吞吐，设备侧看 Xid 与 ECC 的趋势。这些数字没有哪个是现成告警能给你的，得自己搭采集、自己定基线。

经验被重估。十年里练出的判断力——看曲线知道要不要升级、听业务方描述能圈出故障域——在新栈上一半仍然可用，另一半需要重新证明它成立。转型最难的不是学新工具，而是接受自己原有的判断力要在新场景里再过一遍验证，而这个动作几乎没人会在转岗通知里告诉你。

分工重新谈判。模型岗与运维岗要在同一间会议室里重划边界：训练任务失败后谁负责恢复，推理副本的容量谁定，账单上的 token 算在哪个团队头上。书里的章节按技术栈分层，现实里的责任按团队切，两者对不上时要以现实为准——这也是第六篇把门禁、责任与治理单独拎出来讲的原因。

## AI 迭代太快，那该写什么

引擎的调度机制半年换一次实现，并行策略的名字一年改一轮口径，工具互通协议从主仓库拆出去单独迭代。作者动笔前先问的不是“写什么”，而是“写什么不会被下一个版本作废”。

作者的处理办法是把会过期的和不会过期的分开摆。会过期的：产品名、控制台入口、接口参数、指标名、仍处于实验阶段的特性版本号。这些只在正文出现处标注写作时间与所依据的文档，过期了就是过期了，不假装它稳定。不会过期的：一次请求从接入到落盘的生命周期、容量上限从哪条曲线上读出来、评测门禁与灰度怎么设、故障怎么分层收敛、成本怎么归因到账单上的那一行。这两类内容在书里严格分开——主干是方法与判据，具体名称只是它们落在某一条技术栈上的样例；第 27 章把这件事收成一句“关注不变量”。

## 信息读不过来时，作者建议的三个动作

不是所有的更新都值得追。作者给自己和读者定了三条：

先分清机制与版本。看到“某引擎支持某特性”，先问它解决的是哪一段瓶颈——预填充排队、显存碎片、还是长上下文的重复计算。说不清瓶颈的特性，可以暂时不看。

每个结论先问测量位置。同一个首 Token 时延，在客户端、网关、引擎三处测出来不相等，拿不同位置的数字互相比较是最常见的自欺。书里凡涉及时延与吞吐，都会写明数字从哪一层取。

二手数字不进脑子。中文自媒体与二手转述里的加速倍数、开销微秒数、利用率健康区间，多半是转述时丢了前提条件的结果。作者的做法是回原论文或官方文档，取不到一手出处的数字就不写进书——这条对读者同样适用：把外部信息当成待验证的假设，用自己集群的实测基线替换掉它。

## 图与校验

`diagrams/*.mmd` 是图源的唯一权威，`figures/*.svg` 是本地 mermaid-cli 的渲染产物，正文只引用 SVG 路径。渲染关闭 HTML 标签，避免 GitHub 与 Word 端丢字；单图宽度控制在印刷页宽以内；未定稿的书稿一律不经外部渲染服务出图。

`tools/bookcheck/check.py` 守四件事：目录条目与正文标题逐字一致、图引用与图源文件成对且不超标、表格每行列数一致、术语统一与全角标点。

## 关于作者

作者的岗位轨迹是云计算架构师、区块链基础设施架构师、AI 架构师，2020 年起转到销售侧，现任 FDE（Forward Deployed Engineer，前置部署工程师）。岗位换过几轮，做的其实是同一件事：把还没人跑稳的东西跑稳。云时代要稳的是资源池与租户边界，区块链时代是节点、共识与链上数据的可追溯，到了 AI 时代换成了卡、网络，以及一次请求的真实成本。转到销售侧之后，稳的定义又多出一层：先弄明白对方到底要什么，再谈技术选型。岗位在变，问题的形状一直很像——约束在最底层，责任在中间层，而用户只感知最上面那一层。

FDE 的位置也决定了这本书的写法。这个岗位坐在客户现场与产品团队之间，一边要接住对方说不清楚的需求，一边要把自己环境的约束讲回去，中间那段没人翻译就交付不了。做销售的这几年，见过的失败项目里技术选错的原因反而少，多数是需求没问清、预算没对齐、责任没落到具体的人头上——这三件事恰好都在运维岗与算法岗的交接缝上。书里反复出现的两句要求——先确定故障落在哪一层再选诊断工具，每个结论先问测量位置——不是文体偏好，是在这种接缝上被逼出来的习惯。

书中以阿里云公共云作为案例环境，只因为它提供了一条端到端可归因的完整路径；这不构成对任何厂商的评价，也不代表作者任职机构的立场。

## 适合谁

做过 Kubernetes、数据库、中间件或私有云运维，现在即将参与 GPU 集群、推理服务或训推平台的工程师。读它有一个前提：愿意在自己的环境里把数字跑出来——书里每一条判据都要靠复现才成立，只看结论不实测，能力不会长出来。

不适合两种期待：想找模型结构与训练算法的理论推导，或者想要一份现成的厂商选型答案。本书不评价厂商优劣，也不提供选型结论；给出的是诊断与验证方法，结论需要你在自己的集群上重新确认。

## 写在最后

转型最难的阶段往往不在技术上，而在身份上。你会有一段两边都不完整的日子：旧场景里刚学的新名词派不上用场，新场景里养了十年的直觉接二连三被证伪。这种状态持续多久，很大程度取决于你手上有没有一条完整路径可以走通一次。走通一次，位置感就回来了，也不必再靠别人转述的数字判断自己是不是落后。这本书能做的就是把那条路径写清楚，剩下的一段要在你自己的集群上走。
